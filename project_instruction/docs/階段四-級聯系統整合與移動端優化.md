# 階段四：級聯系統整合與移動端優化

本階段對應論文中的 **Stage~4（級聯閾值調優）** 與 **Stage~6（移動端導出）**。前面階段已經完成：

- Stage~1：MobileNetV4 輕量級過濾器  
- Stage~2：EfficientNetV2-B3 精準專家（+ 可選 GenConViT）  
- Stage~3：LightGBM 元模型（分析用，可選）

階段四的目標是：

1. 把 Stage~1 與 Stage~2 串成一個完整的兩階段級聯推理流程；  
2. 在 combined validation 上離線搜尋最佳的兩個閾值 $(\tau_{\mathrm{low}},\tau_{\mathrm{high}})$，在給定 Stage~2 使用率預算下最小化 FNR；  
3. 將最終模型與閾值導出為適合移動端使用的 TorchScript + metadata bundle，並進行基本的延遲與大小評估。

> 註：早期計畫中的「per-video 動態閾值」與完整 QAT+KD 流程目前尚未實作。現階段實作重點是 **靜態兩閾值級聯 + post-training quantization (PTQ)**，並把系統級 trade-off 明確地暴露出來。

---

## 任務 4.1：兩階段級聯推理邏輯（CascadeDetector）

**子目標**：實作並維護一個級聯推理類（例如 `CascadeDetector`），封裝 Stage~1 + Stage~2 的推理流程，以及 $(\tau_{\mathrm{low}},\tau_{\mathrm{high}})$ 兩個閾值的路由邏輯。

概念流程：

1. 載入 Stage~1 MobileNetV4 模型與其溫度縮放參數 $T_1$；  
2. 載入 Stage~2 EfficientNetV2-B3 模型與其溫度縮放參數 $T_2$（如有）；  
3. 給定一張預處理後的人臉圖片 $x$：  
   - 計算 Stage~1 偽造機率 $p_1(x) = \sigma(f_1(x)/T_1)$；  
   - 若 $p_1(x) < \tau_{\mathrm{low}}$ → 直接輸出 real；  
   - 若 $p_1(x) > \tau_{\mathrm{high}}$ → 直接輸出 fake；  
   - 否則 → 將 $x$ 升級至 Stage~2，計算 $p_2(x)$，並以固定閾值（例如 0.5）做最終決策。

你可以用下面這類 Prompt 讓 LLM 幫你維護 `src/stage4/cascade_detector.py`：

> 「請閱讀 `src/stage4/cascade_detector.py`，確保它：  
> 1. 使用兩個固定閾值 $(\tau_{\mathrm{low}},\tau_{\mathrm{high}})$ 控制是否升級到 Stage~2；  
> 2. 支援載入經溫度縮放校準的 Stage~1/2 模型；  
> 3. 對外提供簡單的 `predict_image` / `predict_batch` 介面，回傳最終標籤與中間分數（便於之後分析）。」

## 任務 4.2：級聯閾值調優（Grid Search + 系統級指標）

**子目標**：在 combined validation 上以 grid search 尋找多個代表性的 $(\tau_{\mathrm{low}},\tau_{\mathrm{high}})$ 組合，並記錄對應的：

- FNR（假陰性率）、FPR  
- Stage~2 escalation rate $\pi_2$  
- Stage~1 leakage rate $\pi_{\mathrm{leak}}$

實作要點（與論文 Results / Discussion 一致）：

1. 使用已訓練並校準好的 Stage~1/2 模型，在 combined validation manifest 上預先 compute 並 cache logits；  
2. 掃描一個合理的 grid（例如 $\tau_{\mathrm{low}} \in [0, 0.2]$、$\tau_{\mathrm{high}} \in [0.5, 0.8]$，步長 0.01）；  
3. 對每組 $(\tau_{\mathrm{low}},\tau_{\mathrm{high}})$，計算上述指標並存入表格；  
4. 挑出幾個 Pareto-optimal operating points，例如：  
   - FNR ≈ 0.006，$\pi_2 ≈ 0.0116$（安全優先）；  
   - FNR ≈ 0.0054，$\pi_2 ≈ 0.0150$（平衡 mobile 部署）。

對應腳本通常會放在 `src/tools` 或 `src/stage4` 下，例如 `tune_cascade_system.py` / `benchmark_cascade.py` 等。若需用 LLM 修改，可用以下類型 Prompt：

> 「請閱讀 `src/stage4/benchmark_cascade.py`（或 `src/tools/tune_cascade_system.py`），確認它：  
> - 使用預先生成的 logits + labels 進行離線 grid search；  
> - 正確計算 FNR、Stage~2 escalation rate 和 Stage~1 leakage rate；  
> - 把最佳配置輸出為 JSON/CSV，供論文與部署使用。」

## 任務 4.3：移動端導出與量化（TorchScript + PTQ）

**子目標**：將 Stage~1 和 Stage~2 模型導出為 TorchScript 格式，並應用 post-training dynamic quantization (PTQ) 以降低模型大小與 CPU 推理成本；同時把最佳閾值 $(\tau_{\mathrm{low}},\tau_{\mathrm{high}})$ 與溫度參數一併封裝成 metadata。

目前實作重點：

- 使用 `torch.jit.trace` / `torch.jit.script` 將已訓練的 Stage~1/2 模型轉換為 TorchScript；  
- 利用 `torch.quantization.quantize_dynamic` 對線性層做 INT8 量化；  
- 將量化前後的模型大小與桌面 CPU 延遲差異記錄成表格（對應論文附錄與 Mobile 部分）；  
- 建立簡單的 bundle 結構，例如：

```text
mobile_bundle/
  stage1.ts                 # TorchScript Stage 1 model (quantized)
  stage2.ts                 # TorchScript Stage 2 model (quantized)
  config.json               # 包含 tau_low, tau_high, T1, T2 等
  version.txt               # 版本與日期
```

對應腳本可以集中在 `src/stage4/optimize_for_mobile.py` 與 `src/stage4/mobile_deployment/onnx_exporter.py` 中。若要擴展為 ONNX 或未來的 QAT+KD，可以在這一階段預留參數與結構，但不在當前專題中強制實作。
