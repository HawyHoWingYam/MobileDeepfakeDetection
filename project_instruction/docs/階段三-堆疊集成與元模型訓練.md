# 階段三：堆疊集成與元模型訓練（可選分析模組）

本階段對應論文中的 **Stage~3 LightGBM 元模型**。在最終系統設計中，Stage~3 \*不是\* 必須元件，而是作為一個 **分析工具** 來回答兩個問題：

1. EfficientNetV2-B3 與（可選的）GenConViT 之間是否存在可挖掘的互補性？  
2. 在已經很強的單一專家基線之上，堆疊集成（stacking）是否能帶來穩定、實質的性能提升？

實驗結論（與論文一致）是：

- 使用 EfficientNetV2-B3 特徵、並以 LightGBM 作為元模型的 Stage~3，在 combined validation 上 **略低於** 最佳單一專家（AUC 0.9610 vs 0.9633，F1 0.8869 vs 0.8930，FNR 輕微上升）。  
- 因此，Stage~3 不適合作為最終部署的決策頭，但它仍然有價值：可以驗證「目前專家已捕捉到大部分可用訊息」，並為未來加入更多異構專家（例如音訊、文字或其他視覺模型）預留接口。

下面的任務說明，主要是為了讓你或後續研究者能夠理解並維護 `src/stage3` 下的腳本，而不是要求在每次實驗中都必須啟用 Stage~3。

---

## 任務 3.1：生成元模型訓練集（create_meta_dataset.py）

**子目標**：使用 `create_meta_dataset.py`，從已訓練好的 Stage~2 專家模型中構建一個「無偏」的 meta-dataset，用於之後訓練 LightGBM 元模型。

在目前的實作中，流程概念如下（與論文 Method 對應）：

1. 使用多資料集訓練 manifest，定義 K 折（例如 K=5）的資料劃分。  
2. 對每一折 $k$：
   - 在訓練折上訓練（或重新訓練）EfficientNetV2-B3 專家模型；  
   - 在對應的驗證折上，以 evaluation 模式跑 EfficientNetV2-B3（以及可選的 GenConViT），抽取 logits 與中間層嵌入向量；  
   - 將這些 **Out-of-Fold 特徵 + 真實標籤** 存入暫存檔。
3. 所有折結束後，將暫存檔合併，得到覆蓋整個訓練集的 meta-dataset（例如 `meta_features.npy` + `meta_labels.npy` 或對應的 CSV）。

在使用 LLM 幫你維護或擴展這個腳本時，可以給出類似的引導提示（簡化版）：

> 「請閱讀 `src/stage3/create_meta_dataset.py`，確保它在以下方面與目前專案保持一致：  
> 1. 只依賴已完成的 EfficientNetV2-B3 Stage~2 專家（GenConViT 僅作為可選附加特徵來源）；  
> 2. 使用 K-Fold 產生 out-of-fold meta-dataset，避免資料洩漏；  
> 3. 產出包含特徵矩陣 X\_meta 與標籤 y\_meta 的檔案，方便之後用 LightGBM 訓練元模型。」

> 「請在程式中加入清晰的日誌（logging）與進度條（tqdm），並在註解中說明為何需要 out-of-fold 特徵，以及這樣做如何避免在元模型訓練中重複使用同一筆資料的標籤資訊。」

實務上，你可以根據算力決定是否啟用完整的 K-Fold 流程；在目前最終系統並不依賴 Stage~3 的前提下，meta-dataset 的生成頻率可以降低。

## 任務 3.2：訓練 LightGBM 元模型（train_meta_model.py）

**子目標**：使用任務 3.1 構建的 meta-dataset，訓練並評估一個 LightGBM 元模型，分析它相對於單一 EfficientNetV2-B3 專家的實際增益（或損失）。

目前程式碼中的 `src/stage3/train_meta_model.py` 主要步驟應包括：

1. 載入 meta-dataset（X\_meta, y\_meta）。  
2. 使用簡單的 train/val 切分（例如 90%/10%）做內部驗證，以避免 overfitting。  
3. 以 `lightgbm.LGBMClassifier` 為基礎，進行輕量的超參數搜尋（learning_rate, num_leaves, max_depth, 正則化係數等）。  
4. 在驗證集上報告 AUC、F1、FNR 等指標，並與 Stage~2 EfficientNetV2-B3 的單模型結果對照。  
5. 儲存最終元模型權重（例如 `meta_model.pkl`）與訓練摘要（例如 `meta_summary.json`），方便在論文或附錄中引用。

你可以用下面這種 Prompt 來請 LLM 幫你檢查或改寫這個腳本：

> 「請閱讀 `src/stage3/train_meta_model.py`，確保它使用 LightGBM 作為 Stage~3 元模型，並在 combined validation 上輸出 AUC、F1、FNR 等指標，以便與 Stage~2 EfficientNetV2-B3 專家比較。請在程式中加入清楚的註解說明：  
> - 元模型在目前實驗中的表現略低於最佳單一專家；  
> - 因此最終部署不啟用 Stage~3，而是將其視為分析工具。」

## 3.3 本階段與最終系統的關係

總結來說，階段三的「正確角色」是：

- **不是** 必需的部署模組，而是 **分析與研究模組**；  
- 用來量化「在現有專家下，stacking 的實際收益有多大」，並為未來加入更多異構專家預留方向；  
- 透過負面結果，提醒後續工作：在強基線之上，ensemble 並不總是自動帶來提升。

當你完成本階段的實驗與分析之後，可以在專題報告與論文的 Discussion / Ablation 中加入這樣的結論：  

> 「在本專案設定下，LightGBM 元模型（Stage~3）在 combined validation 上平均略低於最佳的 EfficientNetV2-B3 專家，且增加了不少實作與部署成本。因此，最終系統採用兩階段級聯（Stage~1 + Stage~2）作為主路徑，並保留 Stage~3 作為分析工具與未來擴展的基礎。」

接下來，便可以帶著這些結論進入 **階段四**，把兩階段級聯、元模型實驗以及 Stage~4 閾值調優與移動端 export 串連起來。
