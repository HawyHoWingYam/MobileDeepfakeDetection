\paragraph{Task Definition.} We frame deepfake detection as binary classification at the frame/image level: \emph{real} (\texttt{label=0}) vs.\ \emph{fake} (\texttt{label=1}). For videos, our manifests reference extracted face crops; training and evaluation operate at the frame/image granularity to maximise sample size and label fidelity, while downstream applications may aggregate predictions per video (e.g., majority vote or max probability) if needed. This choice keeps the core task simple and aligns with common evaluation practice on FF++/CelebDF/DFDC \cite{rossler2019faceforensicspp,li2020celebdf,dolhansky2020dfdc}.

\paragraph{Datasets.} We train on four academic datasets---CelebDF\,v2, FaceForensics++, DeeperForensics\,1.0, and DFDC---and hold out Deepfake\hyp Eval\hyp 2024 as an out\hyp of\hyp distribution (OOD) benchmark. CelebDF\,v2 provides high\hyp quality face\hyp swap videos of celebrities designed to challenge detectors \cite{li2020celebdf}; FaceForensics++ aggregates multiple manipulation methods (DeepFakes, Face2Face, FaceSwap, NeuralTextures, etc.) under controlled conditions \cite{rossler2019faceforensicspp}; DFDC is a large\hyp scale crowd\hyp sourced dataset with diverse actors and compression pipelines \cite{dolhansky2020dfdc}; DeeperForensics\,1.0 emphasises real\hyp world perturbations and challenging textures \cite{jiang2020deeperforensics}. Deepfake\hyp Eval\hyp 2024 adds contemporary in\hyp the\hyp wild content collected from TrueMedia.org and social media platforms in 2024, covering 88 websites and 52 languages \cite{deepeval2024}. We use Deepfake\hyp Eval\hyp 2024 strictly for cross\hyp dataset validation/testing.
We adopt a unified $256\times256$ PNG face\hyp crop specification for all preprocessed datasets, following common practice in MobileNet/EfficientNet\hyp based detectors and balancing fidelity against on\hyp device latency. In addition to these training/evaluation sources, we reference the DF40 dataset introduced in DeepfakeBench~\cite{zhang2024deepfakebench} as a public benchmark that already uses $256\times256$ PNG face crops; DF40 itself is not included in the training or evaluation splits for the experiments reported in this paper, but its format informs compatibility with newer in\hyp the\hyp wild benchmarks.

\paragraph{Preprocessing Pipeline.} All video datasets are preprocessed into face\hyp crop images using a configurable pipeline (cf.\ \cite{rossler2019faceforensicspp,li2020celebdf,jacob2017integeronly} for similar face\hyp crop protocols). Frames are sampled at a fixed interval (\verb|frame_interval=10|), faces are detected with MTCNN (minimum face size \verb|min_face_size=20|, thresholds \mbox{$[0.6,0.7,0.7]$}), cropped around the bounding box with \verb|bbox_scale=1.3|, and resized to $256\times256$ pixels. We cap redundancy by keeping at most 50 faces per video (\verb|max_faces_per_video=50|). These parameters are versioned alongside the manifests so that the training set can be regenerated or audited.

The preprocessing stack supports multiple video backends (e.g., OpenCV, TorchVision, Decord) and face detectors (MTCNN, InsightFace, YOLOv8, MediaPipe, RetinaFace), but our final experiments use MTCNN with GPU\hyp accelerated decoding for simplicity and reproducibility. Processed images are organised into train/validation/test splits for each dataset, with separate folders for real and fake faces, and accompanied by CSV manifests that record the necessary metadata for every crop. This approach maintains a simple underlying file layout while making manifests the primary interface for the tasks of training, evaluation, and audit.

\paragraph{Manifest Generation and Structure.} After preprocessing, we produce CSV manifests that are the canonical index of all our experiments. Each row of a manifest corresponds to a single face image and includes (at the least) a \texttt{image\_path}, \texttt{label}, \texttt{split} and \texttt{dataset}; further fields such as \texttt{md5}, \texttt{valid}, \texttt{width}, \texttt{height} and \texttt{file\_size} can be used for integrity checks. In this way Table~\ref{tab:dataset_sizes} is derived directly from the manifests. All sampling, hard\hyp example mining, and evaluation components operate on manifest rows rather than raw folders, making it easy to extend the pipeline to new datasets by regenerating manifests.

\paragraph{Split Protocol and Balancing.} We adopt a simple and reproducible split protocol. For each dataset, preprocessed faces are partitioned into train/val/test splits according to configuration ratios, preserving official test lists when available (e.g., CelebDF\,v2 and FF++). We then construct balanced manifests per dataset and split by sampling equal numbers of real/fake faces. For multi\hyp dataset training, we concatenate these manifests and treat each dataset as a source domain; the combined manifest is approximately balanced both by class and by dataset, so Stage~1 and Stage~2 loaders can rely on standard shuffling rather than complex per\hyp batch reweighting. An earlier weighted sampler remains available in the codebase but is not used in our final experiments.

To guard against trivial path\hyp based leakage, the manifest pipeline can optionally sanitise or reject samples with tell\hyp tale substrings (e.g., directory names that encode \verb|/fake/| or \verb|/real/|). These checks are primarily useful when integrating new corpora; for the curated datasets considered here, manifests are derived from neutral directory layouts and the leakage check is disabled by default.

\paragraph{Augmentation and Normalization.} Stage~1 employs a compact torchvision transform pipeline that resizes images to \SI{256}{px}, applies random horizontal flip, colour jitter, small random affine transformations, and a light Gaussian blur, and normalises with ImageNet statistics. Augmentation is symmetric across classes, with a modest probability of colour/geometry perturbations. This design follows contemporary data augmentation practice for image classification while avoiding heavy corruptions that could distort robustness analysis~\cite{buslaev2018albumentations,pei2024deepfakesurvey}. Stage~2 uses slightly stronger geometric and colour jitter when beneficial; all stages share the same input resolution and normalisation to simplify deployment and quantization.

\paragraph{OOD Evaluation Protocol.} For cross\hyp dataset evaluation, we follow Stage~5 and treat Deepfake\hyp Eval\hyp 2024 as a held\hyp out OOD benchmark \cite{deepeval2024}. We evaluate (i) a calibrated two\hyp stage cascade (Stage~1 + Stage~2 + thresholds tuned on the in\hyp distribution validation set) and (ii) a Stage~2\hyp only upper bound that bypasses Stage~1 and uses the expert on all samples. The tables (Table~\ref{tab:deepeval_calibrated}, \ref{tab:deepeval_stage2only}) summarise accuracy, F1, FNR, FPR, and Stage~2 rate on the Deepfake\hyp Eval\hyp 2024 val/test splits. The sizable performance gap relative to in\hyp distribution validation underscores the importance of robustness studies and future domain adaptation; in this work we focus on low\hyp friction mitigations such as temperature scaling and threshold sweeps~\cite{guo2017calibration,minderer2021revisiting}, and avoid OOD\hyp specific fine\hyp tuning unless justified by target data.

\paragraph{Mobile Evaluation Subset.}
To evaluate on\hyp device performance without requiring the full multi\hyp gigabyte datasets on a smartphone, we construct a compact \texttt{mobile\_eval} subset. This subset is derived by stratified sampling from the four training datasets (CelebDF\hyp v2, FaceForensics++, DFDC, DeeperForensics\,1.0), selecting representative face crops from each source. We sample 1--2 frames per video from a broad sweep of videos, to target $\sim$150--200 images total.

The resulting subset is then split into two directories: \texttt{images\_real/} (72 images) and \texttt{images\_fake/} (80 images); ground\hyp truth labels are determined according to which directory an image belongs to. The Android app can thus determine an image's label by its filesystem path, and compute accuracy without the need for human labeling.

The \texttt{mobile\_eval} subset is (1)~a snapshot that makes it easier and faster to iterate while developing the app without needing to move large datasets back and forth, (2)~small enough so that we have reproducibly measured latency and accuracy on\hyp device for measurement, and (3)~small enough that we can still do a few full runs of tests in a given testing session. We intentionally reuse processed face crops from our PC pipeline so that on\hyp device and desktop evaluations run on pixel\hyp identical images (besides any JPEG re\hyp encoding due to transfer); all reported on\hyp device metrics in Section~\ref{sec:mobile} refer to this subset.
