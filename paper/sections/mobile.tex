% Overview paragraph
To enable practical deployment on resource\hyp constrained mobile devices, we developed a native Android application that runs the two\hyp stage cascade entirely on\hyp device. The same Stage~1 (MobileNetV4) and Stage~2 (EfficientNetV2\hyp B3) weights trained on desktop are exported to ONNX format and bundled into the application package. Alongside the weights, we export the calibrated temperatures from the Stage~1 and Stage~2 temperature\hyp scaling procedures (Section~\ref{sec:pipeline_overview}) and embed them into a lightweight cascade configuration JSON used by the app. This approach ensures that (1)~user media never leaves the device, preserving privacy; (2)~the cascade thresholds and calibration temperatures tuned on the PC validation set transfer directly to mobile without re\hyp fitting; and (3)~performance characteristics remain consistent across platforms.

The application supports four detection modes: \emph{single image} selection from the gallery, \emph{batch} processing of multiple selected images, \emph{video} frame\hyp by\hyp frame analysis with configurable sampling rate, and \emph{folder} traversal for evaluation of entire directories. All detection results are logged to a structured CSV file that records timing breakdowns and cascade routing decisions, enabling systematic performance analysis.

%----------------------------------------------------------------------
\paragraph{On-device Pipeline.}
The inference pipeline on Android mirrors the desktop cascade with minor adaptations for the mobile runtime environment:

\begin{enumerate}[leftmargin=*,itemsep=2pt]
  \item \textbf{Image acquisition}: The user selects an image or video from the system gallery or document picker; for videos, frames are extracted at a configurable interval (default: 1 frame per second, maximum 200 frames).
  \item \textbf{Face detection and cropping}: A lightweight face detector (Android's built\hyp in \texttt{FaceDetector} API) locates the primary face region; if no face is detected, a center crop is applied as fallback.
  \item \textbf{Preprocessing}: The cropped region is resized to $256\times256$ pixels and normalized using ImageNet statistics ($\mu=[0.485,0.456,0.406]$, $\sigma=[0.229,0.224,0.225]$).
  \item \textbf{Two-stage cascade inference}: ONNX Runtime for Android (v1.19.0) executes the cascade with the same threshold logic as the desktop version: if $p_1 < \tau_\mathrm{low}$ the sample is classified as real; if $p_1 > \tau_\mathrm{high}$ it is classified as fake; otherwise Stage~2 is invoked for the final decision using $\tau_\mathrm{s2}$.
  \item \textbf{Result display and logging}: The predicted label, confidence score, cascade stage used, and per\hyp phase timing (preprocessing, inference, total) are displayed to the user and appended to a persistent detection log.
\end{enumerate}

\paragraph{Application Features.}
The Android app provides several detection modes tailored to different use cases:

\begin{itemize}[leftmargin=*,itemsep=2pt]
  \item \textbf{Single image}: Select one image from the gallery; the app displays the face crop preview and final result including label, confidence, stage used, and timing breakdown.
  \item \textbf{Batch detection}: Select multiple images for sequential processing; upon completion, a summary shows total count, number of detected deepfakes, Stage~2 usage rate, and average latency per image.
  \item \textbf{Video detection}: The app extracts frames at 1\hyp second intervals (up to 200 frames) and processes each frame independently, reporting the proportion of deepfake frames and average per\hyp frame latency.
  \item \textbf{Folder detection}: A directory picker allows selecting an entire folder; all images and videos within are processed recursively, enabling evaluation of test sets like \texttt{mobile\_eval}.
\end{itemize}

\paragraph{Detection Logging.}
All detection results are appended to \texttt{detection\_logs.csv} in the app's external storage directory. Each row contains: timestamp, source URI, predicted label, binary deepfake indicator, confidence score, cascade stage, preprocessing time (ms), inference time (ms), total time (ms), threshold values ($\tau_\mathrm{low}$, $\tau_\mathrm{high}$, $\tau_\mathrm{s2}$), the Stage~2 calibration temperature, and a flag indicating whether Stage~2 was invoked. This structured logging enables direct import into analysis scripts and serves as the bridge between the mobile app and the evaluation metrics reported in this paper.

\paragraph{On-device Evaluation Setup.}
We evaluated the deployed cascade on a Xiaomi~13 smartphone featuring a Qualcomm Snapdragon~8~Gen~2 system\hyp on\hyp chip with an octa\hyp core CPU configuration: $1\times$ Cortex\hyp X3 @ 3.2\,GHz, $2\times$ Cortex\hyp A715 @ 2.8\,GHz, $2\times$ Cortex\hyp A710 @ 2.8\,GHz, and $3\times$ Cortex\hyp A510 @ 2.0\,GHz. The device has 8\,GB LPDDR5 RAM and runs Android~13. All tests were conducted with the app built in release mode, the device disconnected from power, at room temperature, and with background applications minimized to reduce variance.

Timing measurements are captured within the application: \texttt{preprocess\_ms} covers image loading, face cropping, and tensor conversion; \texttt{inference\_ms} measures ONNX Runtime execution of Stage~1 and (if triggered) Stage~2; \texttt{total\_ms} is the wall\hyp clock time from image selection to result display. The reported statistics are averages over all samples in the test run.

On the \texttt{mobile\_eval} subset (152 images), the cascade achieves an average total latency of approximately 180\,ms per image, with Stage~2 invoked for only 7.2\% of samples under the default threshold configuration. The first inference after app launch incurs a one\hyp time model loading overhead of approximately 500\,ms; subsequent ``warm'' inferences average around 180\,ms. For batch and folder detection modes, this startup cost is amortized across all samples.

\paragraph{PTQ vs.\ QAT.}
We adopt post\hyp training dynamic quantization (PTQ) for linear layers due to its simplicity and strong accuracy\hyp size trade\hyp off on our models. Quantization\hyp aware training (QAT) can further reduce the quantization gap by learning with simulated quantization noise, at the cost of training complexity and longer cycles; recent surveys provide an overview of PTQ/QAT trade\hyp offs for vision models~\cite{gholami2021quant_survey}. As complementary levers, pruning and knowledge distillation reduce compute and model size with modest accuracy loss~\cite{blalock2020pruningsurvey,gou2021kdsurvey}. We plan to evaluate per\hyp channel INT8 and selective INT4 for heads/backbone under the same export pipeline.

\paragraph{Compute Savings.}
Let $C_1$ and $C_2$ denote the per\hyp frame compute costs (or latencies) of Stage~1 and Stage~2, and let $e$ be the Stage~2 escalation rate under a given threshold configuration. The expected per\hyp frame cost of the cascade is
\[
  \mathbb{E}[C] = C_1 + e\cdot C_2,
\]
since all samples pass through Stage~1 and only a fraction $e$ are escalated. In our tuned configurations on the combined validation set, $e$ ranges from roughly \num{0.0116} to \num{0.0150} (Table~\ref{tab:cascade_best}), meaning that fewer than \num{2}\% of frames reach the expert. On the \texttt{mobile\_eval} subset, $e \approx 0.072$, resulting in slightly higher average latency but still achieving substantial savings compared to a Stage~2\hyp only system.

\paragraph{Limitations and Future Work.}
The current on\hyp device evaluation has several limitations that suggest directions for future work:

\begin{itemize}[leftmargin=*,itemsep=2pt]
  \item \textbf{Single device}: We report results on one flagship smartphone; multi\hyp device evaluation across different SoC tiers (mid\hyp range, entry\hyp level) would characterize performance variability.
  \item \textbf{Static images only}: While video detection is implemented, systematic video\hyp level evaluation (aggregating frame predictions) remains future work.
  \item \textbf{No hardware acceleration}: The current implementation uses CPU inference only; enabling NNAPI or GPU delegates in ONNX Runtime could reduce latency.
  \item \textbf{Basic face detection}: The Android \texttt{FaceDetector} API is deprecated and less accurate than modern solutions like MediaPipe; integration with a robust face detector would improve preprocessing quality.
  \item \textbf{Energy profiling}: Battery and thermal measurements during continuous detection would provide practical deployment guidance.
\end{itemize}

Despite these limitations, the on\hyp device results demonstrate that the two\hyp stage cascade maintains low false\hyp negative rates and practical latency on representative mobile hardware, validating the feasibility of privacy\hyp preserving deepfake detection on consumer smartphones.
