% Mobile Deployment Section
\label{sec:mobile}

% Overview paragraph
To enable practical deployment on resource\hyp constrained mobile devices, we developed a native Android application that runs the two\hyp stage cascade entirely on\hyp device. The same Stage~1 (MobileNetV4) and Stage~2 (EfficientNetV2\hyp B3) weights trained on desktop are exported to ONNX format and bundled into the application package. Along with the weights, we also export the Stage~1 and Stage~2 temperature\hyp scaling calibrated temperatures from the main paper (Section~\ref{sec:pipeline_overview}) and embed them into a lightweight cascade configuration JSON that is also used by the app. Ultimately this achieves the following: (1)~user media never leaves the device, (2)~cascade thresholds and the temperatures we tune on the PC validation set transfer to mobile without needing to be re\hyp fit, and (3)~performance characteristics are preserved.

It supports four distinct detection modes \hyp{} single image selection from the gallery, detect multiple selected images at once, show frames of a video for frame\hyp by\hyp frame analysis, sampling every nth frame, and walking through folders for evaluating an entire directory's worth of images. All detection results are logged to a structured CSV log file of timing breakdowns and decisions regarding which cascade were hit, so you can analyze your performance across detections.

%----------------------------------------------------------------------
\paragraph{On-device Pipeline.}
The inference pipeline of Android is similar to that of the desktop cascade with slight modifications to suit the mobile runtime environment:

\begin{enumerate}[leftmargin=*,itemsep=2pt,parsep=0pt]
  \item Image acquisition: The user selects an image from the system gallery or document picker, or a video; frames are sampled from the video at a configurable interval (default 1 frame per second; max. 200 frames).
  \item Face detection and cropping: A lightweight face detector (Android's built\hyp in \texttt{FaceDetector} API) finds the approximate region around the primary face; in the case of a missing face, a center crop is applied here as a fallback.
  \item Preprocessing: The cropped region is resized to $256\times256$ pixels and normalized using ImageNet statistics ($\mu=[0.485,0.456,0.406]$, $\sigma=[0.229,0.224,0.225]$).
  \item Two\hyp stage cascade inference: if $p_1 < \tau_{\mathrm{low}}$ then we classify the sample as real; if $p_1 > \tau_{\mathrm{high}}$ we classify the sample as fake, else we invoke Stage~2 for final decision using $\tau_{\mathrm{s2}}$.
  \item Result display and logging: display predicted label, confidence score, stage used, per\hyp phase timing (preprocessing, inference, total) and append to persistent detection log.
\end{enumerate}

\paragraph{Application Features.}
The Android app supports various modes of detecting faces:

\begin{itemize}[leftmargin=*,itemsep=2pt,parsep=0pt]
  \item A single image: the user selects an image from their gallery and we display the face crop preview and final result (label, confidence, stage used, timing breakdown).
  \item Batch detection: the user selects multiple images for us to process and display a summary afterward (total count, number of detected deepfakes, Stage~2 usage rate, average latency per image).
  \item Video detection: the app extracts frames every second (up to 200 frames) and processes each frame separately. It then reports the percentage of deepfake frames and the average per\hyp frame latency.
  \item Folder detection: provide the UI with a directory picker allowing the user to select a folder. Each image and video file within the folder is processed recursively allowing the user to evaluate large test sets (for e.g. the static\hyp image subset \texttt{mobile\_eval}).
\end{itemize}

\paragraph{Detection Logging.}
All detection results are appended to \texttt{detection\_logs.csv} in the app's external storage directory. Each row contains: timestamp, source URI, predicted label, binary deepfake indicator, confidence score, cascade stage, preprocessing time (ms), inference time (ms), total time (ms), threshold values ($\tau_{\mathrm{low}}$, $\tau_{\mathrm{high}}$, $\tau_{\mathrm{s2}}$), the Stage~2 calibration temperature, and a flag indicating whether Stage~2 was invoked. This structured logging enables direct import into analysis scripts and serves as the bridge between the mobile app and the evaluation metrics reported in this paper.

\paragraph{On-device Evaluation Setup.}
We evaluated the deployed cascade on a Xiaomi~13 smartphone featuring a Qualcomm Snapdragon~8~Gen~2 system\hyp on\hyp chip with an octa\hyp core CPU configuration: $1\times$ Cortex\hyp X3 @ 3.2\,GHz, $2\times$ Cortex\hyp A715 @ 2.8\,GHz, $2\times$ Cortex\hyp A710 @ 2.8\,GHz, and $3\times$ Cortex\hyp A510 @ 2.0\,GHz. The device has 8\,GB LPDDR5 RAM and runs Android~13. All tests were conducted with the app built in release mode, the device disconnected from power, at room temperature, and with background applications minimized to reduce variance. To keep results broadly applicable, we intentionally use CPU\hyp only inference without NNAPI/GPU delegates, treating the reported latency as a conservative ``worst\hyp case'' baseline that applies even when specialised accelerators are unavailable or misconfigured.

Timing measurements are captured within the application: \texttt{preprocess\_ms} covers image loading, face cropping, and tensor conversion; \texttt{inference\_ms} measures ONNX Runtime execution of Stage~1 and (if triggered) Stage~2; \texttt{total\_ms} is the wall\hyp clock time from image selection to result display. The reported statistics are averages over all samples in the test run.

\paragraph{Runtime Performance.}
Table~\ref{tab:mobile_runtime_auto} summarizes the on\hyp device inference statistics. On the \texttt{mobile\_eval} subset (152 static images), the cascade achieves an average total latency of approximately 180\,ms per image, with Stage~2 invoked for only 7.2\% of samples under the default threshold configuration. Compared to the desktop CPU baseline (Table~\ref{tab:mobile_perf}), mobile latency is roughly $2\times$ higher, which is expected given the lower clock speeds and thermal constraints of mobile SoCs. In the validation sets for Stage~2, it was determined that the escalation rate on mobile devices (7.2\%) was greater than that of desktop devices (1.2\%). This difference in rates, however, are likely attributed to variations within the \texttt{mobile\_eval} data subset rather than instantaneously when comparing each device's individual characteristics.

The first inference after launching the app pays a model loading overhead of around 500\,ms; subsequent ``warm'' inferences are down to roughly 180\,ms. In batch and folder detection modes, this startup cost is amortized across all samples.

\paragraph{Accuracy and Error Rates.}
In Table~\ref{tab:mobile_accuracy_auto}, we enter accuracy on \texttt{mobile\_eval}; cascade gets 92.8\% accuracy, with 2.5\% FNR and 12.5\% FPR. The low FNR means we don't often miss deepfakes---which we did on purpose as a safety feature. The higher FPR means we dipped our toes into the riskier side of the waters, marking some legitimate images as suspicious---that's an acceptable sacrifice if we can manually appraise some false positives.

Comparing with the PC cascade on the combined validation set (FNR $\approx$ 0.6\%, Table~\ref{tab:cascade_best}), the mobile evaluation shows slightly higher error rates. This is attributable to the smaller and differently\hyp distributed \texttt{mobile\_eval} subset rather than degradation from ONNX export. The consistency of low FNR across platforms confirms that the cascade's conservative bias transfers effectively to on\hyp device deployment.

\paragraph{PTQ vs.\ QAT.}
We adopt post\hyp training dynamic quantization (PTQ) for linear layers due to its simplicity and strong accuracy\hyp size trade\hyp off on our models. Quantization\hyp aware training (QAT) can further reduce the quantization gap by learning with simulated quantization noise, at the cost of training complexity and longer cycles; recent surveys provide an overview of PTQ/QAT trade\hyp offs for vision models~\cite{gholami2021quant_survey}. As complementary levers, pruning and knowledge distillation reduce compute and model size with modest accuracy loss~\cite{blalock2020pruningsurvey,gou2021kdsurvey}. We plan to evaluate per\hyp channel INT8 and selective INT4 for heads/backbone under the same export pipeline.

\paragraph{Compute Savings.}
Let $C_1$ and $C_2$ denote the per\hyp frame compute costs (or latencies) of Stage~1 and Stage~2, and let $e$ be the Stage~2 escalation rate under a given threshold configuration. The expected per\hyp frame cost of the cascade is
\[
  \mathbb{E}[C] = C_1 + e\cdot C_2,
\]
since all samples pass through Stage~1 and only a fraction $e$ are escalated. In our tuned configurations on the combined validation set, $e$ ranges from roughly \num{0.0116} to \num{0.0150} (Table~\ref{tab:cascade_best}), meaning that fewer than \num{2}\% of frames reach the expert. On the \texttt{mobile\_eval} subset, $e \approx 0.072$, resulting in slightly higher average latency but still achieving substantial savings compared to a Stage~2\hyp only system.

\paragraph{Limitations and Future Work.}
The current on\hyp device evaluation has several limitations that suggest directions for future work:

\begin{itemize}[leftmargin=*,itemsep=2pt,parsep=0pt]
  \item \textbf{Single device}: We report results on one flagship smartphone; multi\hyp device evaluation across different SoC tiers (mid\hyp range, entry\hyp level) would characterize performance variability.
  \item \textbf{Static\hyp image evaluation only}: While the deployed app supports frame\hyp by\hyp frame video processing, the quantitative on\hyp device benchmarks reported here are restricted to a stratified static\hyp image subset (\texttt{mobile\_eval}); systematic video\hyp level evaluation (aggregating frame predictions) remains future work.
  \item \textbf{CPU\hyp only baseline, no hardware acceleration}: The current implementation uses CPU inference only, providing a universally available baseline even on devices without reliable NNAPI/GPU support; enabling NNAPI or GPU delegates in ONNX Runtime is expected to further reduce latency and is left to future work.
  \item \textbf{Basic face detection}: The Android \texttt{FaceDetector} API is deprecated and less accurate than modern solutions like MediaPipe; integration with a robust face detector would improve preprocessing quality.
  \item \textbf{Energy profiling}: Battery and thermal measurements during continuous detection would provide practical deployment guidance.
\end{itemize}

Despite these limitations, the on\hyp device results demonstrate that the two\hyp stage cascade maintains low false\hyp negative rates and practical latency on representative mobile hardware, validating the feasibility of privacy\hyp preserving deepfake detection on consumer smartphones.
